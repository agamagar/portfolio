# 3D icons - model-side levers
_Researched 2026-09-20. Sources listed at the bottom, numbered; cite by number inline._

Scope: the user attaches a flat 2D icon (subject image) and optionally a second image that shows the target soft-matte 3D look (style image), and asks the model to re-render the icon in that look while keeping silhouette, metaphor and colour. Three targets: Gemini image models (Nano Banana Pro = gemini-3-pro-image, Nano Banana 2 = gemini-3.1-flash-image), GPT Image 2 on the edits endpoint, and Figma's Make an image / Edit with prompt fields. Everything below is what the vendor pages say on 2026-09-20; anything else is marked inference or UNVERIFIED.

## Reference-image roles (subject image vs style image): what each vendor documents

**Gemini.** The request carries images as untyped parts (`{"type": "image", "data": ..., "mime_type": ...}` next to a `{"type": "text"}` part); no code sample on the page adds a role, label or reference-type field to an image part [1]. The "object / character / style" vocabulary exists only as a capacity table, not as a request field: "Gemini 3 image models let you to mix up to 14 reference images. These 14 images can include the following:" then per model, Gemini 3.1 Flash Image = "Up to 10 images of objects with high-fidelity to include in the final image", "Up to 4 images of characters to maintain character consistency", "Up to 3 images to be used as style references"; Gemini 3 Pro Image = "Up to 6 images of objects with high-fidelity", "Up to 5 images of characters"; Flash Lite = "Up to 14 images of objects" and N/A for characters and style [1]. So a "style reference" on Gemini is a budget the model recognises, and the only documented way to mark which image is which is the prose of the prompt. The Limitations list repeats the budgets in words: "gemini-3-pro-image supports 5 images with high fidelity, and up to 14 images in total. gemini-3.1-flash-image supports character resemblance of up to 4 characters and the fidelity of up to 10 objects in a single workflow." [1] The Flash Lite model card adds "Not optimized for multiple reference inputs or multi-turn sequential editing." [1] The general per-request cap is "Gemini models support a maximum of 3,600 image files per request." [2] Recommended wording for pointing at an image, quoted from the editing templates: "Using the provided image of [subject], please [add/remove/modify] [element]" (single image) and "Take the [element from image 1] and place it with/on the [element from image 2]" plus the worked prompt "Take the blue floral dress from the first image and let the woman from the second image wear it." (multiple images) [1]. So Gemini's documented handles are "the provided image", "image 1 / image 2" and "the first image / the second image", in the order the images are attached.

**GPT Image 2 (edits endpoint).** `images` is "Input image references to edit. For GPT image models, you can provide up to 16 images." [6] There is no role field; the Cookbook tells you to build the roles in text: "Multi-image inputs: Reference each input by index and description ("Image 1: product photo... Image 2: style reference...") and describe how they interact ("apply Image 2's style to Image 1"). When compositing, be explicit about which elements move where ("put the bird from Image 1 on the elephant in Image 2")." [7] The prompting guide confirms the index is attachment order: "Pass the scene photograph as image 1 and the dog photograph as image 2. Specify which element to move, its destination, and what must remain unchanged." [5] Single-image edits use "the input image" ("Use the same style from the input image and generate...") [5][7] and "the provided clothing images" [7]. The guide's Image API example describes reference use as "use one or more images as a reference to generate a new image" with the gift-basket prompt "containing all the items in the reference pictures." [4] One mask rule matters for ordering: "If you provide multiple input images, the mask will be applied to the first image." [4]

**Figma.** Make an image: "(Optional) Add a reference image to influence the output. You can: Click Attach image as reference to upload an image from your computer. While the prompt is open, click the blue button that appears on images and other layers on the canvas. Copy any layer from the canvas, then paste it into the prompt box... Drag an image from your computer directly into the prompt box." Edit with prompt takes the selected image as the thing being edited ("Select the image you'd like to edit") and offers the same "(Optional) Add a reference image to influence the edit." [8] So on Figma the subject/style split is structural: for the icon job, the flat icon should be the selected layer under Edit with prompt and the 3D sample should be the attached reference; the help pages never document a role for the reference beyond "influence". The workflows article lists what a reference can stand for: "A mood board or photo for overall style and color direction", "An existing image from the design to match lighting or tone", "A sketch or wireframe to guide composition and layout", "A product or object you want included in the scene" and says to "attach one or more reference images by selecting the plus button in the bottom right of one or more images." [10] No Figma page says how to name the reference inside the prompt (nothing solid found); inference: since Figma routes to Gemini or GPT Image models (see below), the "image 1 / the reference image" wording that those vendors document is the safe bet, with the selected layer as image 1. UNVERIFIED which order Figma sends selected layer vs attached reference.

## Preserving the source (silhouette, colour, metaphor) in words

**Gemini** documents preservation as three moves. (a) Name the unchanged parts in detail: "To ensure critical details (like a face or logo) are preserved during an edit, describe them in great detail along with your edit request." with the template "Using the provided images, place [element from image 2] onto [element from image 1]. Ensure that the features of [element from image 1] remain completely unchanged." [1] (b) The inpainting template: "Using the provided image, change only the [specific element] to [new element/description]. Keep everything else in the image exactly the same, preserving the original style, lighting, and composition." [1] (c) The style-transfer template carries a preservation clause of its own: "Preserve the original composition but render it with [description of stylistic elements]." [1] Multi-turn follow-ups use "Keep everything the same, but change..." and "Do not change any other elements of the image." [1] Gemini also promises that plain edits inherit the source look: "The model will match the original image's style, lighting, and perspective." [1] For our job that promise cuts the wrong way (we want the look replaced, the geometry kept), so the prompt has to split the two explicitly.

**GPT Image 2** says the same thing more procedurally: "For edits, identify what should change and what must stay the same. Refine one thing at a time and inspect the result." [5] "Constraints (what to change vs preserve): State exclusions and invariants explicitly (e.g., "no watermark," "no extra text," "no logos/trademarks," "preserve identity/geometry/layout/brand elements"). For edits, use "change only X" + "keep everything else the same," and repeat the preserve list on each iteration to reduce drift." [7] The guide warns that words are not a lock: "Repeated edits can still change details you intended to preserve. Restate those constraints and inspect each result. If a region must remain pixel-identical, composite the approved edit into the original image instead of relying on prompting alone." [5] Worked preservation lines worth copying: "Do not change anything else." [5][7], "Preserve product geometry and label legibility exactly." [5], "Do not restyle the product" [5].

**Figma** documents no preservation wording at all (nothing solid found); the only tip is "Enter a prompt in the text field. Try to include as much context as possible." [8] Inference: the vendor lines above apply through whichever model Figma is routing to.

For the icon job the documented vocabulary maps cleanly: "silhouette" and "metaphor" are what Google calls "composition" and what OpenAI calls "geometry/layout"; "colour" needs its own clause because the style templates on both vendors invite a new palette ("a dramatic palette of deep blues and bright yellows" [1]; "keep the visual language of a reference image (palette, texture...)" [7]). So say the colours stay and the palette of the style image does not carry over, in words, or the model will do what the templates train it to do.

## Style transfer from a second image: what is documented, what is folklore

**Documented, Gemini.** "Style transfer" is a named editing use case, but the documented form is text-described style applied to ONE image: "Provide an image and ask the model to recreate its content in a different artistic style." Template: "Transform the provided photograph of [subject] into the artistic style of [artist/art style]. Preserve the original composition but render it with [description of stylistic elements]." [1] Two-image style transfer (style from image 2 onto subject of image 1) has no template on the page; the closest is the composition template ("Take the [element from image 1] and place it with/on the [element from image 2]") [1] and the capacity line "Up to 3 images to be used as style references" for Flash Image (and no style-reference row for Pro) [1]. Inference: combine the two documented forms, "Take the icon from the first image... render it in the style of the second image... Preserve the original composition", and still describe the style in words, because every Google template describes the style even when an image is present.

**Documented, GPT Image 2.** Style transfer is named and defined: "Style transfer is useful when you want to keep the visual language of a reference image (palette, texture, brushwork, film grain, etc.) while changing the subject or scene. For best results, describe what must stay consistent (style cues) and what must change (new content), and add hard constraints like background, framing, and "no extra elements" to prevent drift." Worked prompt: "Use the same style from the input image and generate a man riding a motorcycle on a white background." [7] The prompting guide adds the role sentence that is the closest thing to vendor-endorsed two-image phrasing: "Transfer a visual style: Assign the reference image a specific role: its palette, texture, or visual medium. Describe the new subject separately." [5] And the index pattern ""apply Image 2's style to Image 1"" is given verbatim as an example of how to say it [7]. Note the direction in OpenAI's worked example is the reverse of ours (style kept, subject new); our job keeps the subject and swaps the style, so the "what must stay consistent" list has to be the icon, not the style image.

**Figma.** "reach for edit with prompt for broad changes like style, color, and mood" [10] and the reference-image list includes "A mood board or photo for overall style and color direction" [10]. No phrasing, no role slot (nothing solid found).

**Folklore, to keep out of the prompt.** (a) Bracketed tags like `[style reference]` or `<img2>` as if they were parsed: no vendor documents any tag syntax; both document plain English indices. (b) The idea that Gemini has a "style" slot you can set: it is a count in a table, not a field [1]. (c) "In the style of image 2" without a verbal description of the style: every vendor example that names a style also describes it ("swirling, impasto brushstrokes" [1]; "palette, texture, brushwork" [7]). (d) Naming a living artist or a brand's icon set as the style: outside the scope of these docs, and the house rule already bans it. (e) Any claim that Figma exposes a style-strength or fidelity control: not on the help pages (nothing solid found).

## Backgrounds and alpha (white vs transparent)

**GPT Image 2: real alpha, in preview.** API reference: "background: optional "transparent" or "opaque" or "auto" or null. Set the background of the generated image output. gpt-image-2.5-sunburst and gpt-image-2.5-flare, including their 2026-09-08 snapshots, support opaque and transparent backgrounds. Transparent backgrounds are available for supported GPT Image models. For gpt-image-2 and gpt-image-2-2026-04-21, this support is in preview. When using transparent, set the output format to png or webp." [6] The Cookbook confirms it is a true channel and tells you to defend it: "Set background="transparent". Set output_format="png" (the default) or output_format="webp". Both support transparency; jpeg does not... Explicitly request an isolated subject on a fully transparent background, with no scenery, solid backdrop, checkerboard, or unwanted shadows. For edits, explicitly preserve the transparent background in each prompt so later steps do not introduce a new background. Keep the returned image as a PNG or WebP file and preserve its alpha channel throughout downstream processing." and "converting an RGBA image to RGB discards its transparent background." [7] The prompting guide's cutout prompt is the model line: "isolate it on a fully transparent background. Output: centered product, crisp silhouette, no halos/fringing... Do not add a solid backdrop, checkerboard, scenery, or shadow." and the warning "A drawn checkerboard is not transparency." plus "Check the decoded image's alpha channel, including hair, glass, shadows, and object edges." [5] So: the parameter produces alpha; the prompt still has to say "transparent background, no checkerboard, no shadow" or the model may paint one, and a soft-matte 3D icon's contact shadow will get baked into the alpha unless you ask for none.

**Gemini: no alpha documented.** The image-generation page has zero occurrences of "transparent" or "alpha"; output formats offered are image/png and image/jpeg via `response_format` with no background option [1]. Nothing solid found on transparent output for any Nano Banana model. What IS documented is asking for white in the prompt: the sticker template ends "[color/background preference]" and the worked prompt ends "The background must be white." [1]; the page's own icon example is "An icon representing a cute dog. The background is white. Make the icons in a colorful and tactile 3D style. No text." [1] (That last prompt is the nearest thing on any vendor page to our job, and it is text-to-image, not image-to-image.) So on Gemini the icon ships on a flat white field and gets cut out downstream.

**White vs transparent as a prompt choice.** OpenAI's own style-transfer example asks for "on a white background" in words even though the model can do alpha [7], and the instructional-visual prompts ask for "a white background" [5]. Inference from the two vendors together: write the white background into the prompt for every model (it is the only lever on Gemini and it stabilises GPT Image 2 when alpha is off), and add `background: "transparent"` plus the "fully transparent background, no checkerboard, no shadow" sentence only on the GPT Image 2 path. Do not write "transparent background" into a prompt that goes to Gemini or to Figma's Nano Banana routes: the docs give no alpha there, and a model that cannot emit alpha has nothing to do with the word except draw it.

**Figma.** No prompt-level background control is documented; the documented route is "Remove background" as a separate action after generation ("You can use Figma AI to remove the background from any image.") [8]. Nothing solid found on whether Figma passes a background parameter to the GPT Image route.

## Proposed opening sentences for the prompt   (concrete phrasings with rationale + source #)

Each opener is the first one or two sentences; the style description, the preservation list and the background clause follow in that order, matching OpenAI's recommended order "scene, subject, details, and constraints" [5] and Google's "describe what must stay... what must change" split [1][7].

1. **Two images, Gemini (Flash Image or Pro Image):**
   "Take the flat icon from the first image and re-render it as a soft matte 3D icon in the style of the second image. Preserve the original composition: the same silhouette, the same objects and the same colours as the first image."
   Rationale: "the first image / the second image" is Google's own multi-image handle [1]; "Preserve the original composition" is the verbatim clause from Google's style-transfer template [1]; naming silhouette, objects and colours applies Google's "describe them in great detail" rule for the parts that must survive [1]. The style still gets described in the next sentence because every Google style example does so [1].

2. **Two images, GPT Image 2 edits endpoint:**
   "Image 1: the flat 2D icon to re-render. Image 2: style reference only. Apply Image 2's style to Image 1: render the icon from Image 1 as a soft matte 3D icon. Change only the rendering style; keep everything else the same: the silhouette, the metaphor and the colours of Image 1."
   Rationale: index-plus-description and "apply Image 2's style to Image 1" are the Cookbook's verbatim patterns [7]; "Assign the reference image a specific role" is the guide's instruction [5]; "change only X" + "keep everything else the same" is the Cookbook's edit formula [7]. Omit `input_fidelity` on this model (see below) [4][5][6][7].

3. **Two images, Figma Edit with prompt (flat icon selected, 3D sample attached as reference):**
   "Re-render this icon as a soft matte 3D icon in the style of the attached reference image. Keep the icon's silhouette, metaphor and colours exactly as they are; take only the material, lighting and depth from the reference."
   Rationale: Figma documents the selected layer as the edit target and the attachment as "a reference image to influence the edit" [8], and routes to Nano Banana or ChatGPT Images models [9], so this uses the vendor-neutral "this icon / the attached reference image" wording rather than an index whose order Figma does not document (UNVERIFIED which image Figma sends first; this phrasing does not depend on it).

4. **Single image, any model (no style sample):**
   "Using the provided image of a flat icon, re-render it as a soft matte 3D icon. Preserve the original composition, silhouette and colours; change only the rendering: [material, light, depth described in words]."
   Rationale: "Using the provided image of [subject]" is Google's single-image handle [1]; the sentence shape is Google's style-transfer template with the style slot filled by a description instead of an artist [1]; OpenAI's "Use the same style from the input image" is the mirror case and confirms "the input image" as its handle [5][7].

5. **Background clause, appended, per route:**
   Gemini and Figma: "The background must be white. No text." (verbatim register from Google's sticker and icon examples [1]).
   GPT Image 2 with `background: "transparent"` and `output_format: "png"`: "Isolate the icon on a fully transparent background. Do not add a solid backdrop, checkerboard, scenery, or shadow." (verbatim from OpenAI's cutout prompt [5]; the parameter makes the alpha, the sentence stops the model painting a fake one [7]).

6. **Preservation list to repeat on every iteration (all models):**
   "Do not change anything else: keep the silhouette, the objects, their positions and the colours of the original icon." Rationale: "Do not change anything else." is verbatim on both OpenAI pages [5][7]; Google's follow-up form is "Keep everything the same, but change..." [1]; both vendors say to repeat the list each turn because drift is documented behaviour ("repeat the preserve list on each iteration to reduce drift" [7]; "Repeated edits can still change details you intended to preserve." [5]).

### Parameter facts that sit beside the prompt

- **input_fidelity on GPT Image 2: do not send it.** Guide: "For gpt-image-2, omit this parameter; the API doesn't allow changing it because the model processes every image input at high fidelity automatically." [4] Prompting guide table: "input_fidelity: Omit it. Image inputs are always processed at high fidelity." [5] Cookbook model table for gpt-image-2: "Disabled. input_fidelity does not work for this model because output is already high fidelity by default" [7]. The API reference still lists `input_fidelity: optional "high" or "low" or null. Controls fidelity to the original input image(s).` without a per-model note [6], and the Cookbook's own gpt-image-2 edit samples still pass `input_fidelity="high"` [7], which is the contradiction that produced the earlier shipped mistake; the three prose sources agree it is a no-op or rejected on gpt-image-2, so the prompt library should not rely on it for this model. UNVERIFIED whether the server errors or silently ignores it.
- **Prompt length, GPT Image edits:** `prompt: string ... minLength 1 maxLength 32000` [6].
- **Image count:** GPT Image edits "up to 16 images" [6]; Gemini "up to 14 reference images" on Gemini 3 models with the object/character/style budgets above [1]; Gemini 2.5 Flash Image "works best with up to 3 images as input" [1].
- **Which model Figma uses:** the Make/Edit article only says "From the dropdown menu, select an available AI model." [8]. The credits page names the choices and their cost for Make image and Edit image: "2 per image for ChatGPT Images 2.0, 6 per image for Nano Banana 2 Lite, 8 per image for Nano Banana, 16 per image for Nano Banana 2", "as of August 25, 2026" [9]. So Figma's field currently exposes Nano Banana (2.5 Flash Image), Nano Banana 2 Lite, Nano Banana 2 and "ChatGPT Images 2.0". Inference: "ChatGPT Images 2.0" is Figma's label for OpenAI's gpt-image-2 generation; UNVERIFIED. Nano Banana Pro is not in Figma's list on that page. No prompt length limit is stated on any Figma page fetched (nothing solid found).
- **Figma access:** "Available in Figma Design, FigJam, Figma Draw, Figma Slides, Figma Sites, and Figma Buzz. Available on paid plans. Requires edit access to the file." and "Tip: On the Starter plan, you can make an image or edit an image with a prompt through the Figma agent." [8]
